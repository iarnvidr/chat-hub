# Known issues and acceptance limits

- The hosted PR23 debug-native run [41110436605](https://github.com/iarnvidr/chat-hub/actions/runs/41110436605), on source `6b7f1f9a41daf4e9894e4ab946acb1639fa48c9d`, verified official fixture import, library UI body, body full-text search, selection, and alternate-branch detail and persistence in the same default OS-account app-data directory across same-process use, restart, and closure. It did not exercise an alternate home/data-directory override, public DMG installation, provider traffic, or native Save dialog/file acceptance. Raw native IPC health status was not retained separately.
- The native Save commands reuse the consistent SQLite backup and streamed JSON export APIs; JSON export is not a restore format. Existing targets are refused without clobbering, cancellation creates no file, and normal successful receipts confirm durability after sync. Only `Error::ArchivePublished` means publication succeeded but durability could not be confirmed; the UI warns that the file exists. Do not report that nothing was saved or automatically overwrite/retry it. Native OS Save dialog/file acceptance remains unverified.
- Real provider traffic, login/account behavior, provider capture/ingestion, and the advisory provider-capture smoke remain unverified. Capture is disabled by default. Only the exact `chatgpt.com` host is intercepted; subdomains, authentication/sign-in hosts and all other hosts tunnel without TLS decryption. Synthetic Linux tests are not provider acceptance.
- Local detail reads still have an 8 MiB encoded response limit. Accurate escaping/part budgeting admits larger ordinary transcripts, but oversized graphs and individual messages need pagination. Search reads bounded topology separately from transcript text; snippets are excerpts capped at 2,048 Unicode characters. Authoritative stored text is unchanged.
- **Continue in ChatGPT** targets the selected saved ChatGPT conversation in the embedded view; it requires access through the signed-in provider account. Signed-in continuation and reconciliation back into the local copy are not yet accepted. The existing Paseo cache is a local snapshot; automatic refresh from its deployed source and full raw graph reconciliation remain pending.
- The stable updater uses the pinned public key and `releases/latest`; prereleases require manual installation. A controlled 0.1.0→0.1.1 updater fixture verifier accepted the valid payload and rejected a tampered payload with `signature_verification_failed`. This does not prove the genuine unmodified v0.1.1 stable-feed update to v0.2.0, packaged updater UI behavior, or public release acceptance. The genuine baseline check is not automated in the release workflow; feasibility is pending because the production baseline has no debug IPC and runner OS automation permissions/trust and WKWebView automation allowlisting are unverified. The protected approval package must record ordering and a reviewed feasibility plan; no waiver is assumed. See [updater and release status](docs/UPDATES.md).
- The release workflow's hosted production requirements remain: production/native compilation, verified debug bundle, persisted-library smoke, app startup and health, native launch checks, signed updater payload and pinned-key verification, manifest validation, and DMG verification. Provider capture is advisory. These required gates have not been satisfied for the v0.2.0 candidate merely by the PR23 debug smoke or Linux checks.
- Public owner-downloaded DMG installation and downloaded-app quarantine/Gatekeeper behavior remain manual acceptance items. No notarization is provided; ad-hoc signing may trigger Gatekeeper warnings.
- The API uses plaintext HTTP with bearer authentication on loopback. It is trusted-local-only, not suitable for exposure to untrusted networks or protection from local users/processes.
- CA trust is not installed automatically; CA lifecycle and user-guided trust management need further review.
