# Streaming capture: architecture and current limits

This document describes the current proxy capture path. It is a bounded, best-effort observation path alongside forwarding; it is not a durable ingestion pipeline and does not claim that a browser accepted or rendered a response.

## Interception and forwarding

The loopback CONNECT proxy intercepts TLS only for the exact host `chatgpt.com` (case-insensitive). Other hosts are tunneled without TLS interception. For intercepted HTTP/1.1 traffic, requests are forwarded unchanged. When live capture is enabled, JSON `POST /backend-api/conversation` and `POST /backend-api/f/conversation` requests may be tapped up to 512 KiB to retain the just-submitted messages; eight process-wide permits bound retained request bodies to 4 MiB. Oversized, interrupted, or unadmitted request bodies are still forwarded, but their paired stream is not committed. Responses are wrapped in a tee body: each upstream data frame is observed for capture while that frame, along with non-data frames/trailers, is forwarded unchanged. Capture therefore does not reframe or transform the request or response sent onward.

The request context is initialized at entry, before forwarding, with method and path. The current proxy uses the provisional profile scope `provisional:unknown`; the context API also permits a caller to inject a profile scope at entry. The provisional value is a temporary single-profile namespace, not an account identity and not safe for merging multi-account data. The proxy does not currently resolve a global/account profile. Context values are bounded (profile scope 256 UTF-8 bytes, method 32, path 4096); a timestamp and correlation number are also assigned. Debug formatting reports only whether a request body is attached; it never prints message content.

## Bounded capture lane

`CaptureLane` defaults to a 2 MiB maximum per capture, a 16 MiB aggregate retained-byte budget, and an internal queue capacity of 32. It has one worker consuming queued captures. A full per-capture slot is reserved when accumulation begins, rather than charging only bytes already observed. Thus active accumulators and completed captures waiting in the worker queue both count against the retained budget; the reservation travels with queued work and is released when processing completes or work is discarded. If a full reservation cannot be obtained, that capture is marked `Dropped` immediately. This conservative accounting bounds allocation and retained capture memory, at the cost of rejecting work even when a body would have been small.

The queue of legacy `CaptureEvent`s supplied by the caller is a separate bound, controlled by that caller; it is not included in the lane's 32-item queue or 16 MiB budget. The worker uses nonblocking `try_send` for that legacy event. If its queue is full or closed, the result is `Dropped`; it does not clone/retry the body. The observation channel is also nonblocking. A failed observation send increments `lost_observations`; this counter makes reporting loss possible, but cannot deliver an observation when that channel is unavailable. State counters are best-effort runtime counters, not durable records.

`CaptureEvent` remains the existing compatible shape (`host`, `path`, `status`, `body`). `CaptureObservation` separately provides context, response metadata, and a terminal state.

## Completion and terminal states

`Complete` means the proxy observed upstream response-body end-of-stream and the capture was accepted into the lane for worker processing. It does not prove the browser accepted the final bytes: downstream delivery can still fail after upstream EOS. For normal identity-encoded content, the worker attempts legacy event delivery; a full/closed legacy queue changes the observed result to `Dropped`.

The capture states currently include:

- `Interrupted`: the tee/capture is dropped before upstream body EOS, including an upstream body error followed by teardown. An upstream error is forwarded as an error; capture is not declared complete merely because the response began.
- `Oversized`: observed data exceeds the per-capture limit. Capture is abandoned and its reservation released; response forwarding continues unchanged.
- `Dropped`: capacity could not be reserved, the internal lane queue rejected completed work, or legacy event delivery failed.
- `UnsupportedEncoding`: the legacy capture lane received a non-identity encoding, or the live snapshot lane received an unsupported encoding (including stacked encodings). Such a body is not emitted as a JSON snapshot.
- `DecodeFailed`: live gzip or zlib-wrapped deflate decoding failed. The browser response remains forwarded as received.

Capture currently retains data frames only. It does not build a general representation of trailers or other frame metadata; those frames are still forwarded. Successful legacy events are raw response body bytes with response host/path/status. Any JSON interpretation/snapshot is limited to available captured body data; there is no new-turn detection or conversation stitching in this path.

## Integration status and boundaries

### Request-entry ownership update

For live capture using a provisional configured profile, the proxy now resolves immutable ownership at request entry. It accepts matching bounded account-header and JWT account/user claims, rejects duplicate or conflicting identity headers, and stores an opaque digest as `chatgpt:observed:…`. This is observed provider-request evidence, not independent JWT signature verification. The supported claim names follow [OpenAI's token-data implementation](https://github.com/openai/codex/blob/67f0994b532b8740f14b5b738af7b7b2a915b1d6/codex-rs/login/src/token_data.rs); that source does not establish current ChatGPT browser behavior. Explicit caller-attributed scopes retain their injection contract.

Without sufficient account/user evidence, scopes remain `provisional:request:…`: opaque credentials are separated with a process-keyed HMAC, and requests without credentials receive unique scopes. Credentials and decoded payloads are used transiently and are never persisted in the scope or diagnostics. Token rotation or process restart may split provisional histories. No automatic promotion or merging is performed. Local tests cover account switching with reversed response completion, token rotation with known claims, conflicts, anonymous isolation, and persistence into separate library identities. Real provider account acceptance is still required.

The production-ring work is implemented in both explicit builders (`src/proxy.rs` and `src/capture_lane.rs`). This is equivalent to PR6 commit `e18dba5` and preserves the existing `CaptureEvent` / `run` compatibility API. This statement is limited to that production-ring work; it does not claim that other PR6 work is included.

`run_with_capture_context(config, events, limits, observations, profile_scope)` supplies an opaque fixed profile scope. The live-capture path carries that value into the normalized account key. Scope identifiers must be 1–256 ASCII alphanumeric characters or `:`, `-`, `_`, `.`; invalid or overlong values are rejected, because truncating an identity could merge profiles. Distinct stable scopes therefore remain distinct in storage when the caller supplies them. This does not resolve provider accounts: `run_with_capture` continues to use `provisional:unknown`; the Tauri service reads `CHAT_HUB_CAPTURE_PROFILE_SCOPE` and defaults to `provisional:default`. Capture remains disabled unless `CHAT_HUB_CAPTURE_ENABLED=true` (or `1`) is explicitly set. Native multi-account capture is not safe or accepted until the app can resolve/select an account-specific scope; do not switch provider accounts while capture is enabled.

The live lane accepts GET JSON snapshots from `/backend-api/conversation/{id}` and completed SSE responses from both POST generation routes. Both paths support identity, gzip (including concatenated members), and zlib-wrapped deflate within a 2 MiB decoded response limit. Legacy SSE snapshots and the bounded `delta_encoding: v1` operations (`add`, `replace`, `append`, `remove`, and batched `patch`) are replayed into message objects. The v1 decoder bounds paths, cursors, and batched operations, applies inherited operation/path/cursor fields, and rejects unknown operations, malformed pointers, incomplete streams, and inconsistent conversation IDs. SSE replay requires `data: [DONE]`, a complete request body, and full message objects with IDs; the request's messages are merged with streamed messages by ID so the just-submitted prompt and generated reply are indexed. Existing ancestors are linked by parent ID and may remain unresolved until a full GET snapshot is captured. `resume_conversation_token.token` is removed from the locally retained raw SSE record; the original bytes are still forwarded unchanged. The decoder's v1 behavior was cross-checked against the MIT-licensed [Agent Beacon ChatGPT adapter](https://github.com/Asymptote-Labs/agent-beacon/blob/b6439f20a9c166cca2522d55a04bb454fcde05bb/browser-extension/src/adapters/chatgpt.ts) and its [simple-turn fixture](https://github.com/Asymptote-Labs/agent-beacon/blob/b6439f20a9c166cca2522d55a04bb454fcde05bb/browser-extension/fixtures/chatgpt/simple-turn.sse); no third-party fixture contents are vendored. Decompression failure increments `decode_failed`; oversized content increments `oversized`; other and stacked encodings increment `unsupported_encoding`. The desktop polls committed counters and refreshes the conversation list and selected detail after an update. `tests/service.rs` exercises compressed snapshots and synthetic legacy and v1 POST/SSE exchanges through CONNECT TLS, the bounded writer, SQLite, and the authenticated status API; it verifies unchanged request forwarding, prompt/reply persistence, and resume-token redaction. These tests do not validate a real provider account or live browser response. The lane is in-memory and best effort: there is no durable staging or downstream-delivery guarantee. Runtime diagnostics expose counters and response/context metadata only; they do not include captured body contents or credentials.
