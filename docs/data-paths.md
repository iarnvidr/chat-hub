# Data and runtime paths

`CHAT_HUB_DATA_DIR` selects the application data directory; otherwise the platform default is used. `CHAT_HUB_DATABASE` and `CHAT_HUB_CA_DIR` override the SQLite and CA locations. Runtime discovery files are stored in a `runtime/` directory beside the configured database: schema-1 `service.json` contains PID, API/proxy addresses, start timestamp, and the service-generated instance ID; `service.token` contains the API bearer token and must not be copied into logs or diagnostics. On Unix the runtime directory is mode 0700 and files are created mode 0600. An exclusive `service.lock` prevents concurrent writers. If the lock exists, startup refuses to overwrite it and gives manual stale-lock recovery instructions; verify no service is running before removing it. A lock is not automatically considered stale based on PID alone. Startup errors roll back files already created, and owned runtime files are cleaned up on drop/shutdown.

`status` reports database health separately from whether an authenticated `/api/health` request to the advertised API succeeds. It does not create a missing database. Requests are restricted to loopback (both recorded addresses are validated before token lookup or network access), use a bounded token/record size, disable proxies and redirects, and have a one-second timeout covering response headers and body. The streamed health body is capped at 16 KiB before each chunk is appended and then parsed as JSON. Authenticated health must echo both the recorded PID and service-generated instance ID; only an exact match reports `running`. A responding authenticated endpoint with mismatched identity reports `identity_mismatch`; unavailable endpoints report `stopped`. Runtime token contents are never included in status or diagnostics.
