# Data and runtime paths

## Rust CLI/service

`Config::from_env` uses `CHAT_HUB_DATA_DIR` when set. Otherwise it uses the platform default: macOS `~/Library/Application Support/io.github.iarnvidr.chat-hub`, Linux `$XDG_DATA_HOME/io.github.iarnvidr.chat-hub` or `~/.local/share/io.github.iarnvidr.chat-hub`, and Windows `%APPDATA%/io.github.iarnvidr.chat-hub`. `CHAT_HUB_DATABASE` and `CHAT_HUB_CA_DIR` override the database and CA locations; their defaults are `chat-hub.sqlite3` and `ca` inside the selected data directory. `CHAT_HUB_TOKEN`, `CHAT_HUB_BIND`, and `CHAT_HUB_PROXY_ADDR` also configure this CLI/service path. Snapshot capture is disabled by default and requires `CHAT_HUB_CAPTURE_ENABLED=true` or `1` to opt in.

These `CHAT_HUB_*` environment overrides do not configure the production native Tauri app. The Tauri app resolves its data directory with `app.path().app_data_dir()` and `DesktopRuntime` explicitly places `chat-hub.sqlite3` and the CA directory `ca` there. The app-level `service.json` and `service.token` are also stored in that platform-default app-data directory. Only the strictly gated debug `native-smoke` path can use `MUNINN_E2E_DATA_DIR`; that test-only override is not a production setting.

The accepted hosted PR23 debug-native run [41110436605](https://github.com/iarnvidr/chat-hub/actions/runs/41110436605), source `6b7f1f9a41daf4e9894e4ab946acb1639fa48c9d`, verified fixture import, library UI body, body full-text search, selection, and alternate-branch detail/persistence in the same platform-default Tauri app-data directory across same-process use, restart, and closure. It does not validate a native alternate data directory, production packaging, public DMG, provider capture, or native Save dialog/file acceptance. Raw native IPC health was not retained separately.

## Runtime records and permissions

The Rust service stores its runtime discovery files in a `runtime/` directory beside the configured database. Schema-1 `service.json` contains PID, API/proxy addresses, start timestamp, and the service-generated instance ID; `service.token` contains the API bearer token and must not be copied into logs or diagnostics. On Unix this runtime directory is mode 0700 and its files are created mode 0600. An exclusive `service.lock` prevents concurrent writers; startup does not treat a lock as stale based on PID alone. Startup errors roll back files already created, and owned runtime files are cleaned up on drop/shutdown.

`status` reports database health separately from whether an authenticated `/api/health` request to the advertised API succeeds. It does not create a missing database. Requests are restricted to loopback (both recorded addresses are validated before token lookup or network access), use a bounded token/record size, disable proxies and redirects, and have a one-second timeout covering response headers and body. The streamed health body is capped at 16 KiB before each chunk is appended and then parsed as JSON. Authenticated health must echo both the recorded PID and service-generated instance ID; only an exact match reports `running`. A responding authenticated endpoint with mismatched identity reports `identity_mismatch`; unavailable endpoints report `stopped`. Runtime token contents are never included in status or diagnostics.

## Library Save

The native library backend exposes `backup_library` and `export_library_json`. Backup uses SQLite's consistent backup mechanism, not a raw database/WAL copy; JSON export is streamed and is not a restore/import format. Native OS Save dialog/file acceptance remains unverified. Existing destinations are refused rather than overwritten, cancellation creates no file, and normal successful receipts confirm durability after sync. Only a post-publication durability failure (`Error::ArchivePublished`) means the file exists but durability is unconfirmed; the UI warns for that case. Do not automatically overwrite or retry it, and do not report that nothing was saved.
